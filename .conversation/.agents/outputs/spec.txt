  v2 (built on Replit, deployed to GCP)
  One configurable platform for RPM, RTM, CCM, PCM and BHI, with therapeutic templates
  for cardiovascular, diabetes, musculoskeletal and behavioral health. Web workspace,
  patient PWA, and React Native apps. Built and run on Replit during development with
  synthetic data only; production runs on GCP. This version replaces the earlier GCP-first
  specification.


  0. Read this first: build on Replit, deploy to GCP
  The platform is built and run on Replit with synthetic data only, and production runs on
  GCP. The code is written so that moving from one to the other changes configuration, not
  code. Sections 1 to 17 are for Claude Code and the build team. Section 18 is the
  deployment guide for the DevOps team. Section 19 lists the decisions still open.

  The nine portability rules. Claude Code must follow these from the first commit. They are
  what make the GCP move a deployment task and not a rewrite.

     1. GitHub is the source of truth. All work goes through Linear issues, branches and pull
        requests. The Repl is a workspace that pulls from main or a feature branch. Nothing
          lives only in Replit.
     2. All settings come from environment variables. One module, packages/config , reads
        and validates them with Zod at startup and fails fast with a clear message. No other
        file reads process.env .
     3. Every outside service sits behind an adapter chosen by an environment variable.
        Storage, field encryption, email, SMS, video, AI, device vendors and EHRs each have a
         local or console driver for Replit and a production driver for GCP. Section 4 lists
        the drivers.




                                                                                                                 Page 2 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




     4. PHI guard. The setting DATA_CLASS is synthetic or phi . The app refuses to start
          with DATA_CLASS=phi unless APP_ENV=prod and every adapter is a production driver.
          Replit and dev can only run synthetic .
     5. Docker-ready from the first commit. Each service has a Dockerfile. Replit cannot
        build Docker images, so GitHub Actions builds every image on every pull request and
        runs a container smoke test. A broken Dockerfile fails the pull request.
     6. No Replit-only services. No Replit Auth, Replit Database (key-value), or any Replit
        SDK outside the storage adapter. Authentication is Better Auth on Postgres; data is
        Postgres; jobs are BullMQ on Redis.
     7. Twelve-factor behavior. Stateless processes, listen on PORT and 0.0.0.0 , JSON logs
        to stdout, graceful shutdown on SIGTERM, health endpoints, migrations as a separate
          command, writes only to /tmp .
     8. Row-level security must work on Replit. The app connects as a dedicated non-owner
        role without bypass rights, and CI proves one tenant cannot read another's rows.
        Managed Postgres defaults often bypass row-level security, so this is tested, not
        assumed.
     9. Configuration is portable data. pnpm config:export writes a tenant's programs,
          templates, rules and care-plan templates to JSON, and pnpm config:import loads
          them elsewhere. Patient data is never exported this way.

  What Replit is never used for

          Real patient data, real phone numbers or real email addresses of patients.
          A production or customer-facing live service. A Replit deployment may host a demo
          with synthetic data only.
          Anything the DevOps team would have to reverse-engineer later. If it works only
          because of Replit, it is a bug.


  1. Purpose, scope, non-goals
  Build Mahalo Care as one configurable platform that runs RPM, RTM, CCM, PCM and BHI
  for any outpatient group, with therapeutic-area templates (cardiovascular, diabetes,
  musculoskeletal, behavioral health) layered on top. The first customer shape is a multi-site
  specialty group such as Groth Pain & Spine (up to 12 locations, about 10,000 unique
  patients a month, RTM for pain and spine, RPM for hypertension, CCM for pain plus a
  second condition), but nothing in the build is specific to one customer.

  In scope

          Clinician, care-manager and admin web workspace (React).
          Patient web app (PWA) plus React Native patient and clinician companion apps (Expo,
          one codebase for iOS and Android) with Bluetooth devices and HealthKit/Health
          Connect, all in v1 (section 10a).
          Program engine: enrollment, consent, care plans, time tracking, device-day counting,
          exceptions, worklists, notes.
          Billing operations engine with versioned CPT rule packs per program and a
          concurrency matrix across programs.
          Device ingestion (cellular device vendors via webhook first, Bluetooth via the mobile
          app).
          EHR integration: FHIR R4 read, per-vendor adapters (OmniMD first custom adapter),
          PDF export of care plans and notes.
          Secure messaging, SMS, email, in-app video.
          Governed AI (summaries, prioritization, draft notes) with full logging and human sign-
          off.
          Multi-tenant, multi-site, white label.
          Full SDLC: monorepo, GitHub Actions, Linear, Replit build workflow, Docker images,
          Terraform, Cloud Run on GCP.
          A DevOps deployment guide from Replit to GCP (section 18).

  Non-goals (do not build)

          Clinical staffing or any care delivery. Mahalo is platform only.
          Automatic billing determinations or claim submission. The platform prepares evidence
          and reports; the customer's revenue team decides and submits.
          EHR write-back in v1. Read-only FHIR plus PDF export is the documented pattern.
          Diagnosis, medication changes or emergency response by AI.
          Research features (EDC, randomisation). Those live in Mahalo Research; a consented
          bridge is a later project.
          Running production or real patient data on Replit.

  Success criteria for v1.0

          A new tenant with 12 locations, three programs and two therapeutic templates can be
          configured by an admin in one working day with no code change.
          A clinician can enroll a patient, assign a care plan, log time, review a reading exception
          and sign a note in under five minutes end to end.
          The month-end billing report for RPM, RTM and CCM reconciles to the time log and
          device-day log with zero double-counted minutes, proven by automated tests.
          A care plan and a monthly note export as a PDF that a medical records clerk can file in
          any EHR.
          All PHI access is in the audit log; the audit log cannot be edited or deleted by any
          application role.
          The same Docker images that passed CI on Replit-built code deploy to GCP with
          configuration changes only.


  2. Product principles and UX standard
  The product is exception-first: a care manager opens the app and sees the patients who
  need attention today, why, and the next action. Everything else is one click deeper. Old
  RPM and CCM tools fail because they show every reading, every task and every field at
  once; this product hides what is routine.

  Principles (apply to every screen and API)

     1. One record per patient. Readings, check-ins, medications, care plan, time, notes and
          messages all hang off one patient timeline. No program gets its own silo.
     2. Programs are configuration. RPM, RTM, CCM, PCM and BHI are rule packs loaded
          from data, not branches in code.
     3. Exceptions, not feeds. Worklists show prioritized exceptions with an owner. Raw data
        is available on the patient page, never on the home screen.
     4. Time is captured as you work. Every clinical action in the app can start, stop and
        attribute time with one click. Manual time entry is allowed but flagged as manual in
          the audit trail.
     5. Billing evidence is a by-product. The month-end report is generated from the same
        logs the clinician saw all month. There is no separate "billing module" to fill in.
     6. Nothing is deleted. Clinical records are versioned and soft-closed. Audit logs are
        append-only.

     7. Human sign-off on anything AI drafts. Drafts are visibly marked as drafts until a
          named user accepts them.
     8. Fast on a 2019 laptop and a 4G phone. Target p75 route load under 1.5 s and interaction
          under 100 ms. Lists are virtualized and paginated server-side.

  Visual standard (Mahalo Product UI Design System v1.0)

          Tokens: sidebar navy #071C3B , accent indigo #3D36E8 , canvas #FAFBFD , flat cards
          with 1 px borders, 6 px chips, no drop shadows beyond elevation-1.
          Type: Inter for UI, Victor Serif Smooth for entity titles (patient name, program name),
          tabular numerals for readings and time.
          Density: one density setting per user (comfortable and compact). Tables show at
          most 7 columns by default; extra columns are opt-in per user and persisted.
          Color carries meaning only for status: red = needs action today, amber = due soon,
          green = on track, grey = inactive. Never color for decoration.
          Patient app: large type, one task per card, two-tap check-ins, a single home screen
          with today's tasks and a connected-device status strip. Atkinson Hyperlegible is the
          patient-facing face.
          Accessibility: WCAG 2.2 AA, full keyboard navigation in the workspace, screen-reader
          labels on every control, focus states visible.
          Empty states teach: each empty list says what will appear there and offers the first
          action.

  Build with

          Tailwind v4 with the design tokens as CSS variables, shadcn/ui components (Radix
          primitives) restyled to the token set, Lucide icons.
          A packages/ui library holding every component, with Storybook and visual
          regression tests (Playwright screenshots). No component is used in an app before it
          exists in packages/ui . React Native components live in packages/ui-native and
          use the same tokens.
          Figma is the design source. Claude Code reads frames through the Figma connector
          when a screen is specified there; otherwise it builds from this document and the
          component library.
          Replit note: the Repl preview pane is for quick looks only. Visual sign-off happens in
          Storybook and on the dev preview, not in the Replit pane.

  3. Architecture and the three-layer model
  The system is a modular monolith on one Postgres database, split into a web app, an API,
  and a background worker, each built as its own Docker image from one monorepo. It is not
  microservices: one schema, one deploy pipeline, clear module boundaries inside the API
  so modules can be extracted later if load demands it. The same three processes run on
  Replit (as plain Node processes) and on GCP (as Cloud Run services).

           apps/api — Fastify API. Modules: tenancy , identity , patients , enrollment ,
           careplans , observations (readings, ePROs, adherence), rules (thresholds and
          exceptions), worklists , time , billing , documents (notes, PDF), messaging ,
           video , devices , ehr , ai , audit , reporting .

           apps/worker — BullMQ workers for device webhooks, rule evaluation, reminders,
          billing period close, PDF rendering, EHR sync, AI jobs, outbound SMS and email. The
          worker also holds the scheduler: BullMQ repeatable jobs (nightly rule sweep, daily
          device-day roll-up, lmonth-end close) registered at start-up. There is no separate
          scheduler app, so cron works the same on Replit and GCP.
           packages/db — Drizzle schema and migrations. packages/rulepacks — program
          definitions and their JSON schema. packages/contracts — Zod schemas shared by
          API and clients, generated OpenAPI. packages/ui and packages/ui-native —
          component libraries. packages/pdf — HTML templates for care plans and notes.
          packages/config — environment parsing and the PHI guard. packages/adapters —
          the driver interfaces and the local and production drivers (section 4).

  Request path

  Browser or app → web static files and api → Postgres and Redis. On GCP this goes
  through a load balancer with Cloud Armor; on Replit it goes through the Repl's public URL.
  Webhooks from device vendors and EHRs hit api/webhooks/* , are verified, written to an
  inbox table, and acknowledged; a worker processes the inbox. No external call is made
  inside a request handler except auth checks.

  Data flow for one reading

     1. Vendor webhook arrives, signature verified, raw payload stored in ingest_inbox .
     2. Worker normalizes it to an observation row with source, device, unit, measured-at
          and received-at.
     3. The same worker updates device_day for that patient, program and calendar date.
     4. Rule evaluation runs for the patient's active programs; an exception row is created
          or updated (deduplicated by rule, patient and 24-hour window).
     5. The exception appears in the owning role's worklist; a notification goes out if the rule
        says so.
     6. The clinician reviews, acts, and the time taken is logged against the exception and the
        program.

  Replit build environment

          Workspace. One private Repl for the monorepo, connected to the GitHub repository,
          named members only, two-factor on every account. No public Repls. Secrets hold
          synthetic and test credentials only; no production credential ever enters Replit.
          Builder. Claude Code is the default builder and runs in the Replit shell or on a
          developer's machine, pushing branches to GitHub. Replit Agent may be used on a
          feature branch for UI work; it reads replit.md , which mirrors the rules in CLAUDE.md .
          Either way, code reaches main only through a reviewed pull request (section 15).
          Files that configure Replit. .replit (run command pnpm dev , port mappings,
          deployment target), replit.nix (Node 22, pnpm, Chromium and its libraries, a
          Postgres client, optionally Redis), and replit.md (rules for the agent). These are in
          git so any developer can recreate the Repl.
          One command. pnpm dev starts the API, the web app, the patient PWA and the
          worker together. pnpm setup installs, migrates, seeds a demo tenant with three
          programs and 50 synthetic patients, and starts everything.
          One origin. The Vite dev server on the Repl's external port proxies /api and
           /webhooks to the API. On GCP the load balancer does the same with path rules. This
          keeps cookies, CORS and webhook URLs identical in both places. VERIFY which ports
          Replit exposes externally and map them in .replit .
          Database. Use Replit's built-in Postgres or an external Postgres 16 (Neon, Supabase or
          similar). VERIFY the major version matches production. Create a dedicated app role
          with CREATE ROLE app_rw LOGIN that is not the owner and does not have bypass-
          RLS rights, give it only the needed grants, and run migrations with the owner role
          through DATABASE_MIGRATE_URL . Set FORCE ROW LEVEL SECURITY on every tenant
          table. Managed Postgres default roles often bypass row-level security, so a CI test
          connects as the app role and proves tenant A cannot read tenant B.
          Redis. Replit has no managed Redis. Use an external Redis with TLS (Upstash, Redis
          Cloud) or run Redis from Nix inside the Repl. BullMQ needs the noeviction memory
          policy; VERIFY the provider allows it.
          PDF rendering. The worker needs Chromium. Install it through Nix, set
           CHROMIUM_PATH , and prove it renders a care plan in milestone 0. In Docker the worker
          uses the Playwright base image pinned to the same Playwright version as the lockfile.
          No Docker on Replit. Replit cannot build or run Docker images. So Dockerfiles are
          validated in GitHub Actions on every pull request, and integration tests run against
          the Repl's database with TEST_DB_MODE=url (a throwaway schema created and


                                                                                           Page 15 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




          dropped per run), while CI uses TEST_DB_MODE=testcontainers .
          What runs where. Replit runs unit tests, API integration tests, the app and quick
          smoke checks. Full Playwright suites, Maestro mobile flows, image builds, security
          scans and migration up-down-up checks run in GitHub Actions, because Replit's
          memory and CPU are limited.
          Mobile. The Expo Metro server can run in the Repl and testers open the app in Expo
          Go for UI work. Bluetooth, HealthKit and Health Connect need native modules that
          Expo Go does not include, so those use EAS development builds installed on real
          devices. VERIFY the Metro tunnel works from the Repl.
          Replit Deployments. A Replit deployment may host a demo for the team or a prospect
          with synthetic data only. It is never given real patient data or live vendor credentials.

  GCP target (production)

  5. Data model (Drizzle schema)
  One Postgres schema, every tenant-owned table carries tenant_id , and Postgres row-
  level security enforces tenant isolation under the application role. Claude Code writes
  these as Drizzle tables in packages/db/src/schema/<module>.ts , one file per module
  below, with a migration per PR.

  Conventions (enforced by lint and a schema test)

          Primary keys are UUID v7 so rows sort by time. Generate them in the application (a
          small uuidv7() helper) so the schema does not depend on a database extension that
          may differ between Replit's Postgres and Cloud SQL.
          Every table has created_at , updated_at (timestamptz, UTC) and created_by (user
          id or system ).
          Every tenant table has tenant_id not null; composite foreign keys include
           tenant_id so a row can never reference another tenant.
          RLS policy on every tenant table: tenant_id =
          current_setting('app.tenant_id')::uuid , with FORCE ROW LEVEL SECURITY on.
          The API sets this per request inside a transaction. The application connects as



                                                                                                                                Page 17 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




           app_rw , a role that is not the table owner and has no bypass-RLS right. A separate
           platform_admin role bypasses RLS for support, and every such use is audited.
          Migrations run as the owner role only.
          No hard deletes on clinical tables. Use status columns and closed_at . A
           deleted_at column exists only on message , notification and task .
          JSON columns ( jsonb ) are validated by a Zod schema in packages/contracts on
          write; the Zod schema name is recorded in a column comment.
          Times a patient acts on (readings, check-ins, device days) are stored in UTC with the
          patient's IANA timezone on the patient row; the device-day date is computed in the
          patient's timezone and stored as a date .
          Money is never stored; the platform stores units, minutes and days. Rates belong to
          the customer.
          Use only Postgres features available on both Replit's database and Cloud SQL (plain
          SQL, jsonb , pg_trgm , exclusion constraints with btree_gist ). Migrations create
          the extensions they need with CREATE EXTENSION IF NOT EXISTS ; VERIFY both are
          allowed on the Replit database in milestone 0.

  7. Billing engine
  The billing engine is a pure function: given an enrollment, a period, the rule pack version,
  and the committed time entries, device days, interactions, consents and care-plan state
  inside that period, it returns the evidence per code and the blockers. It never writes to the
  tables it reads. Because it is pure, it is fully unit-testable and the same code runs live in
  the UI and at month-end close.

  Periods


                                                                                                                               Page 33 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




          A calendar-month period is created for every active enrollment on the 1st of the
          month in the tenant timezone, and on activation for mid-month starts.
          A rolling 30-day supply period for RPM and RTM starts on the first counted device day
          after setup or after the previous period ends. Periods never overlap for one
          enrollment.
          Period close runs at 02:00 tenant time on the 1st for the previous month, and daily for
          rolling periods that ended the day before. Close freezes billing_evidence ,
          generates billing_line candidates, and locks the time entries inside the period
          (status stays committed , billing_period_id set, further edits require reopen).
          Reopen is a tenant-admin action with a reason; it is audited and re-runs the evidence
          calculation.
          Close and roll-up jobs are BullMQ repeatable jobs and are idempotent: running one
          twice for the same period gives the same result and creates no duplicates. This
          matters on Replit, where a process can restart at any time.

  Minute counting (the rule that must never break)

     1. A minute belongs to exactly one time_entry , and one time_entry belongs to
          exactly one program. Overlapping committed entries for the same user are impossible
          (database exclusion constraint).
     2. Only committed entries count. Drafts and voided entries never count.
     3. The entry's user_credential_snapshot decides which bucket it fills: practitioner
          minutes or clinical-staff minutes, as the rule pack defines. Entries from credentials
          the rule pack does not list are shown as "not countable" in the UI at the moment they
          are logged, not discovered at month end.
     4. Only entries whose activity_code is in the rule pack's activity list count.
     5. No rounding. 19 minutes is 19 minutes. Thresholds are compared exactly.
     6. Add-on units are whole blocks beyond the base threshold: for 99458, units =
        floor((minutes − 20) / 20), capped by max_units .
     7. When a patient is enrolled in two programs that both accept the same activity, the
          clinician picks the program when starting the timer. The default is the program whose
          worklist item opened the timer. The UI shows a running tally per program for the
          month so staff can see what is still short.

  Device-day counting




                                                                                             Page 34 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




          A device day is a calendar date in the patient's timezone with at least one valid
          observation from a source the rule pack counts (RPM: FDA-cleared device; RTM: the
          template's declared therapeutic streams, device or patient-reported as the code
          allows).
          Multiple readings on one day are one day. Readings received late but measured inside
          the period count for the measured date if they arrive before period close; after close
          they are recorded as late and excluded, with a visible note.
          Invalid readings (out of physiologic range, device error, duplicate) never count and are
          listed on the patient page with the reason.

  Live interaction evidence

  An interaction with is_live_two_way = true (phone or video with the patient or
  caregiver) inside the calendar month satisfies the management-code requirement for
  RPM and RTM. Secure messages and SMS never satisfy it. The UI shows "live interaction:
  none yet this month" on the patient header for RPM and RTM enrollments.

  Care plan lifecycle

     1. Created in draft from the template when the enrollment is created; prefilled from
          EHR conditions and medications where an EHR link exists (every prefilled field is
          marked source: ehr until a user confirms it).
     2. Signed by a user with the sign_care_plan permission. Signing validates required
          elements, stores a PDF, and sets active .
     3. Any edit after signing creates a new version in draft ; the active version stays active
          until the new one is signed. Diff view between versions.
     4. Review tasks are generated on the template cadence; completing a review logs time
          and a care_plan_review row.
     5. On discharge the plan is closed with a reason and a final PDF.

          or an emergency instruction. Prompts forbid it and an output classifier blocks those
          phrases; blocked drafts are logged and shown as "not available".
          Acceptance, edit and rejection rates per capability are reported monthly to Mahalo
          product; a capability with under 50% acceptance is reviewed.

  13. Security, privacy and compliance
  The platform is built to HIPAA Security Rule controls from the first commit, aligned with
  Mahalo's existing ISO 27001, SOC 2 Type II and ISO 13485 programs. Compliance is a
  property of the code and infrastructure, not a document written afterwards. Building on
  Replit is safe only because no real patient data is ever there; the controls below make that
  a technical fact, not a promise.

  Replit build-phase controls

          Synthetic data only. The PHI guard ( DATA_CLASS ) stops the app from starting with
          real data outside production, and the seed and simulator tools generate every record.
          Private Repl, named members, two-factor on every account, no shared logins. Replit
          Secrets hold test credentials only; production secrets exist only in GCP Secret
          Manager.

          MFA (TOTP or passkey) is mandatory for every workspace user; the tenant may add

          Role-based access with location scope. Permissions are checked in the API on every
          route through one authorize(user, action, resource) function; the UI only hides
          what the API forbids.

  14. Multi-tenancy, multi-site and white label
  One deployment serves many tenants; one tenant has many locations; one patient has
  one home location and can be seen at any location by staff whose role covers it. This is the
  model to confirm live with the customer (their "master location" question), and the data
  model already supports every variant they are likely to describe.

  Tenant isolation

          Shared database, row-level security on tenant_id , one API, one deploy. A tenant can
          be moved to a dedicated Cloud SQL instance later without code change because
          every query already carries tenant_id .
          Tenant resolution is a setting, TENANT_RESOLUTION . subdomain (production):
           groth.care.mahalo.health selects the tenant. membership (Replit and dev): Replit
          gives no wildcard subdomains, so the tenant comes from the user's membership after
          login, with a dev-only ?tenant= switch for seeded demo tenants. Patients resolve by
          the invite link or the app build.
          Per-tenant settings: timezone, region, branding, consent texts, default programs,
          payer overrides, feature flags, data retention.
          Per-tenant rate limits and storage quotas with alerts, so one tenant cannot degrade
          another.

  Locations and the home-location model

           patient.home_location_id is the billing and reporting home. It appears on every
          billing line and defaults from the enrolling location.
          Changing it is an audited action with a reason; the change applies to future periods
          only, and the current open period keeps the old location unless billing staff explicitly
          reassign it.

  Working in Replit (the daily loop)

     1. Open the Repl, fetch from GitHub, and check out the branch for the Linear issue.
          Never commit directly to main from the Repl.
     2. Run Claude Code in the Replit shell (or locally), make the change, and run pnpm dev
          to see it. Use the seeded demo tenant and the device simulator for data.
     3. Run pnpm lint typecheck test and the API integration tests ( TEST_DB_MODE=url )
          in the Repl. Push the branch; GitHub Actions runs the full set.
     4. Fix what CI finds, open the pull request as a draft, then a human marks it ready.
     5. After merge, pull main into the Repl. Configuration files ( .replit , replit.nix ,
           replit.md ) are in git; if the Repl drifts, recreate it from git rather than editing by
          hand.
     6. Secrets are set once per Repl in Replit Secrets from docs/runbooks/replit-

  Database migrations

          Drizzle migrations are generated and committed; a migration must be backward
          compatible with the previous release (expand first, contract in a later release). CI
          runs up, then down, then up on a seeded database.

           DATABASE_MIGRATE_URL , never at API start-up. On GCP this is a Cloud Run job that
          runs before each deploy.
          Destructive migrations require an ADR and a tenant-admin notice.

  Quality gates for release

          Coverage: 85% on billing , time , rules , rulepacks ; 70% elsewhere.
          Zero open critical or high security findings.
          All Playwright flows green on the target environment: enroll, consent, assign device,
          receive reading, exception to resolution, log time, sign care plan, sign note, close
          period, approve line, export PDF.
          Runbooks updated if any operational step changed.

          On Replit: JSON logs in the console and a /healthz and /readyz endpoint per
          service; enough to debug, not a substitute for production monitoring.
          On GCP: dashboards for request latency and error rate per service, queue depth and
          job failures, webhook success rate per vendor, period-close duration, AI acceptance
          rate.
          Alerts to a Mahalo on-call rotation: API 5xx over 1% for 5 minutes, queue backlog over
          1,000, webhook failure rate over 5%, period close not finished by 04:00 tenant time,

          incident review as an ADR-style document in docs/runbooks/incidents/ .

     # Mahalo Care — Claude Code operating instructions

     ## What this repo is
     Mahalo Care: one configurable platform for RPM, RTM, CCM, PCM and BHI with
     therapeutic templates.
     The full specification is docs/spec/mahalo-care-spec.md. Read the relevant
     section before starting any issue.
     Platform only: we never deliver care, never make billing determinations,
     never write to an EHR in v1.
     We build and run on Replit with synthetic data only. Production runs on GCP.
     The code must work in both with configuration changes only.

     ## How work starts
     - Every task is a Linear issue in team CARE. If asked to do something with no
     issue, create the issue first (title, acceptance criteria, milestone), then
     work.




                                                                                          Page 69 of 86
Mahalo Care Platform — Build Specification v2 (built on Replit, deployed to GCP)




     - Branch: `<LINEAR-KEY>-<slug>` from `main`. One issue per branch. One PR per
     branch, opened as draft.
     - Before coding: read the spec section, read the module's README, run `pnpm
     test --filter <module>` to see the baseline.


     ## Commands
     - `pnpm setup` — first-time setup (install, migrate, seed, start). Works in a
     fresh Repl and locally.
     - `pnpm dev` — start api, web, patient PWA and worker. `pnpm dev --filter
     api` for one.
     - `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm
     test:e2e`.
     - `pnpm db:generate` after schema changes; `pnpm db:migrate` (uses
     DATABASE_MIGRATE_URL); `pnpm db:seed` (demo patients, blocked when
     DATA_CLASS=phi); `pnpm db:seed --reference-only` (rule packs, templates,
     device catalog, instruments, roles: safe in every environment); `pnpm
     seed:month`; `pnpm tenant:create` (platform admin only); `pnpm
     smoke:isolation`.
     - `pnpm contracts:generate` after any route change (regenerates OpenAPI and
     client).
     - `pnpm rulepacks:validate` after any change under packages/rulepacks.
     - `pnpm config:export` and `pnpm config:import` move tenant configuration
     (never patient data).
     - `pnpm sim:device` runs the device simulator against the running API.


     ## Rules that are never broken
     1. No PHI anywhere in this repo, Replit, logs, test fixtures, commit
     messages, PR descriptions or Linear issues. Use synthetic data from
     tools/seed.
     2. Every tenant table has tenant_id, an RLS policy, and FORCE ROW LEVEL
     SECURITY. The app connects as app_rw (not the owner, no bypass). Every query
     goes through the request-scoped db with app.tenant_id set.
     3. audit_log is append-only. Never write UPDATE or DELETE against it.
     4. Only the billing module computes evidence; it never writes time_entry or
     device_day.
     5. One time_entry belongs to one program. Never merge, split or round
     minutes.
     6. AI output lands only in ai_draft. No code path writes AI text into
     clinical tables without a user acceptance event.
     7. CPT codes, thresholds and concurrency rules change only in
     packages/rulepacks with a Linear issue labelled verify-cms linking the CMS
     source, and a clinical-ops reviewer on the PR.
     8. No new UI component outside packages/ui or packages/ui-native. No inline

     colors; use tokens.
     9. Migrations are expand-then-contract and must pass up-down-up in CI.
     10. Secrets only from Replit Secrets (test values) or Secret Manager. Never
     commit a key.
     11. Only packages/config reads process.env. Only packages/adapters imports
     vendor SDKs. Add a driver, never a direct call.
     12. No Replit-only service or SDK outside the storage adapter: no Replit
     Auth, Replit DB, or Replit-specific URLs in code. Everything must also run in
     the Docker images.
     13. The PHI guard stays: DATA_CLASS=phi must refuse to start unless
     APP_ENV=prod and every driver is a production driver.
     14. Jobs are idempotent. Any process can restart at any time.

     ## Coding standards
     - TypeScript strict, no `any`, no non-null assertions without a comment
     explaining why.
     - Zod schema first for every input and output; Fastify routes use the type
     provider; export schemas from packages/contracts.
     - Functions under 50 lines; modules export a small public surface; business
     logic in services, not route handlers.
     - Errors are typed (`AppError` with code and status); never throw strings.
     - Tests next to code: `*.test.ts` unit, `*.int.test.ts` integration,
     `e2e/*.spec.ts` Playwright. Integration tests read TEST_DB_MODE
     (`testcontainers` in CI, `url` on Replit).
     - Comments explain why, not what. No commented-out code.
     - Dates: timestamptz in UTC; convert at the edge using the patient or tenant
     timezone; never use `new Date()` in business logic — inject a clock.
     - Services listen on HOST/PORT from config, log JSON to stdout, handle
     SIGTERM, and expose /healthz and /readyz.

  Step-by-step runbook

     1. Confirm the prerequisites. Google Cloud BAA executed on the organization; billing
          account; domain and DNS access for care.mahalo.health (or the chosen domain);
          BAAs with Twilio, the email provider, Daily and each device vendor; GitHub
          organization admin. Start Twilio 10DLC registration now, because it takes time.
     2. Create the projects. mahalo-care-dev , mahalo-care-stg , mahalo-care-prod
          under a folder with HIPAA-aligned organization policies (no public buckets, no
          external IPs on databases, restricted regions, required CMEK). Link billing.
     3. Enable the APIs in each project: Cloud Run, Cloud SQL Admin, Memorystore for
          Redis, Compute Engine, Service Networking, Secret Manager, Cloud KMS, Artifact
          Registry, Vertex AI, Certificate Manager, Cloud Logging, Cloud Monitoring, IAM and
          IAM Credentials.
     4. Create the Terraform state bucket (versioned, CMEK) and run terraform apply for
          dev: network , kms , registry , storage , sql , redis , secrets , iam .
     5. Create database roles. Connect through the Cloud SQL Auth Proxy from a bastion or
          Cloud Shell and run db-roles.sql : owner role for migrations, app_rw for the
          application, grants, default privileges, extensions. Confirm app_rw is not the owner
          and has no bypass-RLS right.
     6. Set the secrets. DATABASE_URL (app role), DATABASE_MIGRATE_URL (owner role),
           REDIS_URL , AUTH_SECRET , and each provider secret. Replit values are never copied;
          generate new ones.
     7. Configure GitHub. Set repository variables ( GCP_ENABLED=true , project ids, region,
          Workload Identity provider, deployer account) and create GitHub Environments dev ,
          staging and production with required reviewers (two for production).

     8. Build and push images. Merge to main runs images.yml ; confirm the three images
          and their scan results in Artifact Registry.
     9. Run the migration job for dev, then the reference-data seed ( pnpm db:seed --

  Moving configuration, not data, from Replit

  Export programs, templates, rules and care-plan templates on Replit with pnpm
  config:export --tenant <slug> and import them on GCP with pnpm config:import .
  Never move patient rows: Replit holds synthetic data only. Branding assets and consent
  texts come across with the configuration. Review the imported thresholds with the
  Clinical Safety Officer before the tenant goes live.

  production hostname. Do not reuse a replit profile build. TestFlight and Play internal
  builds use the staging profile against staging. Store submission waits until prod passes
  its smoke tests.

          Application: route traffic back to the previous Cloud Run revision (one command or

          Prod smoke tests pass and the penetration-test criticals are closed.

          DNS, wildcard certificate and tenant subdomain live.
          Device vendor webhooks and the vendor accounts point at the production URL and
          secrets.
          EHR connection credentials and allow-listed egress IP confirmed with the customer's
          EHR owner.
          Twilio sender approved; email sender domain verified (SPF, DKIM, DMARC).
          Tenant configuration imported and reviewed; users invited with MFA.

          Backup and restore drill done on staging.
          Mobile apps built from the production profile and approved in the stores.
          Legacy data import (M7) rehearsed on staging with a validation report.

  After cutover: retire Replit from the production path

  Shut down any Replit deployment used for demos that pointed at real vendor accounts,
  rotate every secret that was ever stored in Replit, remove the external Redis and
  database used during the build, and keep the Repl only as a synthetic-data sandbox.
  Record the retirement as ISMS evidence.
